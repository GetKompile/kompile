## 2026-07-06 (loop cont.4) — encoder "re-imports ONNX every start" premise was WRONG (loads .sdz); 27s = non-persistable DSP-plan JIT; real fix = graph-opt cache

**Premise-inverting finding (verified read-only, nothing run — box reserved for the user's dl4j BGE build).** Suspected the bge encoder re-imports ONNX on every subprocess start (→ slow + hits the dl4j dup-`input_ids` importer bug). Subagent + my own read of `SameDiffEncoder.loadSameDiffModel` (line 787: `SameDiff.load(modelPath.toFile(), true)`) **disprove it** — the encoder loads a pre-serialized `.sdz` (native SameDiff FlatBuffers) from `~/.kompile/models/encoders/bge-base-en-v1.5/model.sdz`; the `model.onnx` in the same dir is never touched at runtime. ONNX import happens ONCE (offline/staging), not per-start. So the user's premise was wrong; I surfaced that rather than "fixing" a non-problem.

**What the 27s warmup actually is — and a CORRECTION (I was wrong, user was right).** I (and the subagent) first claimed the DSP plan JIT (`DSP plan ready: [32×512] (27809ms)`) is "non-persistable by ND4J's design." **That is false.** ND4J has a full **`DspPlanDiskCache`** (`org.nd4j.autodiff.samediff.execution`): serialized plans are written to `~/.kompile/cache/dsp/dsp_plan_cache/` (`dsp_<structureHash>.bin`/`.meta`), enabled by default (`-Dnd4j.dsp.planCache.diskEnabled`, default true), with cross-JVM model-identity lookup. Our cache dir already holds ~19 MB of plans. So the plan IS persisted across restarts. **Why we still saw 27s every start:** the `.meta` records a `nativeBuildFingerprint` (with the native `BuildStamp`), and the loader rejects any plan whose fingerprint ≠ the current native's `buildInfo()` (DspPlanDiskCache:214) — and dl4j was being actively REBUILT, so each new native invalidated the cached plans (correct behavior: never replay a plan across native versions). **Implication:** once the dl4j native is STABLE (post-rebuild, single vintage in the uber), the first crawl compiles the plan once + caches it, and every subsequent embedding-subprocess restart on that same native HITS the disk cache (`log.info "DSP disk cache HIT"`) and skips the 27s. So there is NO kompile fix and NO dl4j ask here — I incorrectly added one; the mechanism exists and works. The only operational note: a fast dogfood restart loop needs a stable dl4j native (no rebuilds between crawls) for the plan cache to hit. Verify on the next stable-native crawl by grepping the embedding log for `DSP disk cache HIT`.

**The ONE real per-restart redundancy (fixed):** after loading the `.sdz`, `loadSameDiffModel` always ran `applyGraphOptimization()` (matmul+bias fusion, several seconds) on every restart. Fix (subagent, 13 tests, `SameDiffEncoder.java`): fast/slow opt-cache — if `model.opt.sdz` + a `.fp` fingerprint (`size,mtime` of the source) exist and match, `SameDiff.load` the optimized form and SKIP re-optimization; else optimize once → `SDZSerializer.saveOptimized(model.opt.sdz)` + write `.fp`. Graceful fallback (null/exception/corrupt → slow path; save failure non-fatal + deletes partial). Reviewed: clean, package-private helpers for testing, matches the existing `saveOptimized`/`SDZSerializer` convention — not hacky. Side-fix: `anserini/pom.xml` used JaCoCo `@{argLine}` with no JaCoCo configured → literal `@{argLine}` crashed the forked test JVM; switched to `${argLine}` with a default-empty property (pre-existing bug, unblocks the module's tests). Staged for the deferred uber; NOT built/run (BGE building).

## 2026-07-06 (loop) — embedding extract: `toFloatVector` was ALSO per-element GPU-sync; real fix = `data().asFloat()` (VERIFIED 38s→10.3s/batch); CLI clean-error when not in a project

**The extract fix I shipped last iteration was WRONG — caught by guilty-till-proven-innocent.** Last iteration I replaced the encoder's `getFloatsAt` per-element read with `INDArray.toFloatVector()`, believing it did "one `ensureLocation(HOST)` sync." A fresh crawl still degraded to ~36s/batch. A thread dump proved why: in this dl4j build `BaseNDArray.toFloatVector()` (BaseNDArray.java:3561) does `ensureLocation(HOST)` and then **still loops `getFloat(i)`** — and on a CUDA buffer every `getFloat` re-enters `synchronizeHostData → CudaExecutioner.commit` regardless of the earlier ensureLocation. So toFloatVector has the *identical* ~24k-GPU-sync-per-batch cost as the original code. Early batches only *looked* fast because `commit` is cheap when device memory is low; it balloons under memory pressure.

**Real fix (why `data().asFloat()`):** read the dl4j source — `BaseCudaDataBuffer.asFloat()` does `lazyAllocateHostPointer()` + **one** `allocator.synchronizeHostData(this)` for the whole buffer, then `super.asFloat()` which reads via `getFloatUnsynced` (no per-element sync). That is exactly ONE device→host copy per batch. It is also the established kompile bulk idiom (AnseriniVectorStoreImpl / VlmExecutionService / TransEModel / INDArrayConverter). Consolidated both encoder extract paths (batch `extractAllEmbeddings` + single `safeToFloatVector`) onto one bulk extractor: `dup('c')` only when the array is a view/Fortran-order (so `data()` holds exactly the elements in row-major), else `data().asFloat()` directly; defensive trim if the backing buffer is larger than the logical array. No redundant function, matches convention. File: `kompile-app/kompile-data/kompile-search/anserini/.../GenericDenseSameDiffEncoder.java`.

**VERIFIED on a live crawl (fpna-v11, 22 docs, ~5836-node backfill):** distinct-batch CREATE→CREATE dropped from ~38s (exec 10s + ~28s getFloat commits) to **~10.3s (≈ exec only)** — the per-element commit gap is eliminated. exec stayed FLAT at ~10.3-10.6s across the whole backfill (el=104s→965s, 14min) with NO progressive degradation (the earlier 10→60→300s→lane-death climb is gone), ERR=0. Per-batch wall time ~3.7× better; backfill ~1.8h→~30min. The remaining ~10s/batch is the genuine dl4j DSP `exec` (handoff #14). Updated `docs/dl4j-handoff-dsp-embedding-slowness.md` with the corrected scope + a note that dl4j's own `toFloatVector` should delegate to `asFloat` (latent footgun for every CUDA caller).

**CLI: `kompile project start` from a non-project dir crashed with a raw Jackson `FileInputStream` stack** (I hit it deploying — ran `start` from the repo root, which has no `kompile.project.json`). ## 2026-07-06 (loop, iter 7) — THE embedding bottleneck was a kompile per-element getFloat, NOT the DSP

Store-once + guard validated live (HttpTimeout=0, crash=0, ERR=0). But the backfill was still ~4-6 min/CHUNK with the DSP healthy (exec=10s). Broke down one batch cycle: exec finishes, then a **~37s SILENT gap** before the next batch (0 deallocator logs). `model.output()`/exec/VECTORIZED-EXTRACT all log at the SAME instant, so the 37s is elsewhere. **Thread-dumped the embedding-compute thread** → caught it red-handed:
```
GenericDenseSameDiffEncoder.extractAllEmbeddings:2074
 → BaseDataBuffer.getFloatsAt → getFloat (per element)
   → AtomicAllocator.synchronizeHostData → CudaExecutioner.commit   (a GPU→host sync PER ELEMENT)
```
The "OPTIMIZED/VECTORIZED EXTRACT" called `normalized.data().getFloatsAt(offset, batch*dim)`, but on a CUDA `DataBuffer` `getFloatsAt` is a per-element `getFloat` loop and **each `getFloat` triggers a full GPU→host synchronize+commit** → ~24k GPU syncs per forward pass = the ~37s gap.
